### Note A. Prop rule tracking (differentiator, but accuracy-sensitive)

- Schema already carries `max_drawdown`, `trailing_type` (intraday/eod), `trail_lock_*`, `daily_loss_limit`, `profit_target` on `accounts`.
- Model firm rules as **versioned data** (a file in the repo keyed by firm and plan, with an effective date), not hardcoded branches, because firms change rules.
- **Hard limit:** an intraday trailing drawdown depends on the *unrealized* peak during a trade, which the Performance CSV does not contain. From closed trades you can compute an end-of-day trailing drawdown exactly and an intraday one only approximately. Say so in the UI and keep the "informational, may differ from the firm's official figure" disclaimer.
- Consistency and minimum-trading-day rules: start with the ones you personally track across Apex, Tradeify, Lucid and similar, and add on demand.

### Note B. Import adapters (the biggest functional design item)

Today the parser consumes Tradovate's **Performance** export, where each row is already a matched buy/sell **fill pair**; other platforms export raw **executions** or orders that must be paired.

- Introduce an adapter interface: `detect(head: bytes) -> confidence`, `parse(data, tz) -> ParseResult`. The existing parser becomes `TradovatePerformanceAdapter`.
- Add a canonical `executions → fill pairs` pairing step (FIFO per account and symbol) for sources that give executions; the existing `grouping.py` then works unchanged on the resulting pairs.
- **Schema decision to make now, because it is cheap now and painful later:** replace `buy_fill_id/sell_fill_id` integers with `source text`, `buy_ref text`, `sell_ref text`, uniqueness `(user_id, source, buy_ref, sell_ref)`. Tradovate IDs are about 36 billion, so they already exceed 32 bits; other platforms may use strings.
- **Do not build adapters speculatively.** Ask beta users which platform they use and collect real sample files first. Today non-Performance files are rejected with an explanation, which is the right default.

## 7. Baseline benchmark (measured 2026-10-02, before any Postgres work)

`backend/benchmarks/baseline.py` generates seeded synthetic Tradovate exports and times the existing SQLite code. It is the "before" number for the M2 benchmark in section 3: re-run the same scenarios on the Postgres port and compare. Machine: Ryzen 5 3600, 16 GB, Windows 10, Python 3.12.1, SQLite 3.43.1, local SSD, one process, warm cache, no HTTP. Data: one account, 4 instruments, 20 trades a day, 10% of trades scaled in with a second fill pair (so 10,000 trades are 11,031 fill pairs).

| Scenario | Result | Target (doc 01) |
|---|---|---|
| Import one file of 5,506 rows into an empty journal | 1.22 s (parse alone 0.31 s) | under 10 s for 5,000 rows |
| Dry-run preview of that same file (all duplicates) | 0.37 s | none |
| Import one day (20 trades) into a 10,000-trade journal | 12 ms median | none |
| `load_trades`, all 10,000 trades | 390 ms median, 410 ms p95 | none |
| Summary, daily results, score and equity curve over those trades | 45 ms median | none |
| **Dashboard data (accounts, load, compute) at 10,000 trades** | **448 ms median, 458 ms p95** | p95 under 800 ms |
| `load_trades`, one month | 14 ms | none |
| `rebuild_account` (repair tool), 11,031 pairs | 16.1 s (about 1.5 ms a pair, linear) | none |
| `undo_import` of 2,743 rows | 80 ms | none |

**What this tells us** (measured numbers first, then inferences):

1. **Measured: the current code meets both targets with room to spare on a local database**, 8 times under on import and 1.8 times under on the dashboard. The margin is thin on the dashboard once the real costs are added.
2. **Measured: loading rows is 87% of the dashboard time (390 of 448 ms).** The compute step is cheap. Not profiled, but the likely cause is building 10,000 records from TEXT columns (about 11 `Decimal` and date parses each).
3. **Inference, not measured: the importer will miss its target on a network database unless it is rewritten to batch.** It runs about 3 statements per row (look up the pair, insert it, link it to the import), about 16,500 for this file. At 0.5 to 1 ms per round trip to a managed Postgres that is 8 to 16 s, over the 10 s target. The M2 port should look up existing pairs in one query per file and insert with `executemany` or `COPY`. Verify in spike S2 with a measured round trip.
4. **Design consequence for M3: the dashboard endpoint returns aggregates, not trades.** Shipping 10,000 trades as JSON to the browser was not benchmarked and would add serialization and transfer on top of the 390 ms. The trade log is paginated on the server. If Python aggregation is still too slow on Render's smaller CPU, the fallback in doc 02 applies: SQL aggregation, or cached per-user summary rows.
5. **Design consequence for M2: `rebuild_account` and `recalculate_trades` must be background jobs when hosted**, not work done inside a web request (16 s at one heavy user's size).

**Not covered:** concurrent users, HTTP and JSON overhead, Postgres (that is the point of re-running it), multiple accounts, filters other than one month, and the other pages. The synthetic grouping may differ from real exports (real days have more scale-ins and reversals).

## 8. The same scenarios on Postgres (measured 2026-10-03)

`backend/benchmarks/baseline_pg.py` runs the section 7 scenarios through the `tradejournal.pg` modules as one tenant, on PostgreSQL 18.6 on the same machine, with the same seed and data. `--latency-ms N` sleeps N ms before every statement (a batched `executemany` counts once) to model a database a network hop away. Statement counts are printed. It empties the test database first.

| Scenario | SQLite (section 7) | Postgres, local | Modelled +1 ms a statement | Modelled +3 ms | Target |
|---|---|---|---|---|---|
| Import one file of 5,506 rows | 1.22 s | **3.82 s** (138 statements) | 3.97 s | 4.24 s | under 10 s |
| Dry-run re-import of that file | 0.37 s | 0.56 s (9) | 0.57 s | 0.61 s | none |
| Import one day (20 trades) into 10,000 trades | 12 ms | 24 ms | 90 ms | 163 ms | none |
| `load_trades`, all 10,000 trades | 390 ms | 186 ms | 189 ms | 192 ms | none |
| **Dashboard data (accounts, load, compute)** | 448 ms median, 458 p95 | **223 ms median, 254 p95** | 230, 259 | 231, 263 | p95 under 800 ms |
| `load_trades`, one month | 14 ms | 6.8 ms | 9.8 ms | 14 ms | none |
| `rebuild_account`, 11,031 pairs | 16.1 s | 2.0 s (323 statements) | 2.50 s | 3.07 s | none |
| `undo_import` of 2,743 rows | 80 ms | 140 ms (11) | 160 ms | 180 ms | none |

**What this says** (measured numbers first):

1. **Measured: both targets hold with margin on Postgres**, locally and at a modelled 3 ms a statement: the 5,506-row import takes 3.8 to 4.2 s against 10 s, and the dashboard's p95 is about 260 ms against 800 ms.
2. **Measured: the import is about 3 times slower than SQLite locally, and nearly indifferent to latency** (3.82 s to 4.24 s for 3 ms on 138 statements). The cost is the database's own work: in a profile, about 3.2 of 4.7 s was inside statements, mostly the batch insert of fill pairs and the statements that assign pairs to trades, which rewrite indexed columns and check foreign keys. Not tuned: the margin is wide, and `COPY` or fewer indexes are the options if it is needed.
3. **Arithmetic, not run: the doc 05 section 7 inference was right.** The SQLite importer's design (about 3 statements a row, about 16,500 for this file) would add about 16.5 s for every millisecond of latency. The batched port makes 138 statements, so a millisecond adds 0.14 s. The per-row design was never run on Postgres.
4. **Measured: Postgres reads are faster, because rows arrive typed.** Loading 10,000 trades takes 186 ms against 390 ms, since there are no dates or decimals to parse from text. The dashboard is 2 times faster.
5. **Measured: stale statistics cost 60 ms right after a bulk load.** Run before autovacuum had analyzed the tables, one-day imports took 82 ms against 22 ms (`--no-analyze` shows it). Autovacuum normally catches up within about a minute. If the first reads after a signup's big upload matter, the import job can run `ANALYZE` on `fill_pairs` and `trades` itself. Not done.
6. **`rebuild_account` fell from 16 s to 2 s** because it now writes trades in batches. It still holds the user's lock for its duration, so it stays a background job in the design.

**Not covered:** a real network (this is a sleep before each statement: no TLS, no connection pooler, no packet loss), Python and Postgres sharing one machine's CPU (a managed database would not), Render's smaller CPUs, concurrent users and HTTP and JSON overhead (**both are measured below**, in the HTTP load test), and multiple accounts. Run-to-run variation: one run built the large journal in 16.9 s and another in 9.9 s; the other numbers moved by about 10%.

### HTTP load test (measured 2026-10-04)

`backend/benchmarks/load_http.py` serves the real API (all layers: middleware, CSRF, rate limits, the request role, row-level security, the queries) from its own process on a local port, builds a journal for each of 100 people in the test database (99 with 150 trades, one with **10,000 trades**), and has each person look at something every second or so for 40 seconds (the dashboard, the trade log, a trade's page, the accounts, the tags), with optional 5,000-row uploads in the middle. Sessions are the in-memory fakes. **The load generator, the server and the database share one 12-processor laptop**, so these are floors on what a real host would do, not promises; the pool is 10 connections and the server one process (the container's setting).

| Run | Requests | Median | p95 | p99 | Notes |
|---|---|---|---|---|---|
| 100 people, 2 uploads of 5,000 rows | 3,714 in 41 s (90 a second) | 18.5 ms | 359 ms | 467 ms | every answer 200; the uploads took **6.5 s and 7.0 s** while the rest were served (target 10 s) |
| 100 people, no uploads | 3,768 (91 a second) | 12.2 ms | 355 ms | 464 ms | the one big journal's dashboard: median 393 ms, p95 401 ms (target p95 800 ms); its trade log 361 ms, p95 397 ms |
| 100 people, **nobody with a big journal** | 3,963 (96 a second) | 8.4 ms | **29 ms** | 430 ms | the same run with the big journal made small |
| 150 people with almost no pause (about 1,500 a second asked for) | 6,834 (167 a second) | 733 ms | 1.11 s | 1.19 s | every answer 200: no errors, no 503; latency is people divided by throughput |

What this says:

1. **Measured: the targets hold under load.** The 10,000-trade dashboard stays near 400 ms with 100 people on the server (target p95 under 800 ms), and a 5,000-row upload takes about 7 s while others work (target under 10 s). No request failed in any run.
2. **Measured: one big journal sets the tail for everyone.** With the big journal, p95 is 355 ms; with the same journal made small, 29 ms. Median stays at 8 to 12 ms either way. The explanation is **inferred, not profiled**: the dashboard and the trade log of 10,000 trades are about 0.4 s of pure Python (`finance.py` over every trade), the interpreter runs one thread of Python at a time, and while that runs every other request in the process waits. The big person's 18 requests in 40 s are about 17 percent of the time.
3. **Measured: the server saturates near 170 requests a second per process on this machine and degrades by getting slower, not by failing**: at nine times the offered load latency rose to about 0.7 s and nothing errored. (The 5-second pool wait and the timeouts did not trigger, because a closed loop of people cannot queue more requests than there are people.)
4. **What to do with it** (recommendations, not built): **run at least two worker processes** where the plan has two processors (uvicorn reads `WEB_CONCURRENCY`, so it is a host setting, not a code change; the per-process caches and limits then apply to each worker); and when a real person with a big journal appears, move the dashboard's sums into SQL or cache a per-person summary (the fallback already named in doc 02). Neither is needed to meet the targets.
5. One stall of about half a second shows in the maximum of every run (even without the big journal); its cause was not investigated.

**Not covered:** several workers (the session fakes cannot be shared between processes; a run needs the real session store), a real network and a database on its own machine, the screenshots (M6), billing, and a mix with many writes. Run it again against the staging host before the beta opens: `python benchmarks\load_http.py --users 100 --seconds 40` (it empties the test database named in `backend/.env.test`).

**The migration script.** It copies a temporary copy of the single-user journal into one user's tenant in a single transaction (`--dry-run` rolls back), refuses a user who already has data, and ends with a golden check: 26 comparisons that must match (plus 2 informational) of the same facts asked of both databases (row counts, per-account totals and per-day results as exact decimals, and row-by-row fingerprints of accounts, fees, imports, every trade column, fill pairs, tags, notes, screenshot names, day notes and the ledger, matched by what identifies a row rather than by id). Two things found while building it: the comparison must read Postgres rows as tuples (the pool's dict rows silently merge two columns with the same name), and a screenshot file name is unique across the whole database, so two people cannot share one journal file. Not covered: moving the screenshot files (M6, R2).

**`/readyz`.** Ready means the database answers within 2 seconds and has applied every migration the image ships with; a database that is newer than the image is fine (an old container still running during a deploy), an older one is not. It answers 200 or 503 with a state per check (`ok`, `unreachable`, `schema_behind`, `not configured`), never error text, and is not cached. The request role may not read `schema_migrations`, so migration 0005 adds one function, `app_schema_version()`, that returns the newest migration name (a fixed search path, executable by the request role only). The web process boots even if the database is briefly away, and says so. A production process with no `TJ_DATABASE_URL` is alive (`/healthz` 200) but not ready (503): it is not required yet, because the routes still use fakes until M3, and requiring it now would block the Render spike (S4). CI starts the real image both ways. Point Render's health check at `/readyz`, and run the migrations as a release step before the new image takes traffic.

## 10. M3 progress (running log)

The tenant API is built in slices, each one a route family plus the tests that prove it; the front end switches from the sample source to the API source once a screen's routes all exist. Shapes follow `frontend/src/lib/data/model.ts`, which was written first from the design canvas.

**Slice 1 (2026-10-04): the tenant plumbing and the dashboard's reads.** `GET /api/v1/accounts`, `GET /api/v1/filter-options` and `GET /api/v1/dashboard`. The pieces every later route reuses:

- **`Tenant`** (`api/deps.py`): a dependency that authenticates first (an anonymous caller gets 401 even on a server with no database) and then hands the handler one thing, `tenant.session()`, a transaction as the signed-in user. A handler cannot name another user's id; row-level security would refuse it anyway. With no database configured a signed-in call is a 503, never an empty list that looks like "no data".
- **The shared filter** (`TradeFilterQuery`): `preset`, `start`, `end`, `account_type`, `show_archived`, `firms`, `account_ids`, `symbol_roots`, `direction`; unknown or malformed values are a 422 (a misspelled filter must not become a wider answer). **A preset is resolved on the server against "today" in the person's trading-day timezone** (their `trading_day_timezone` and start time), not the server's clock: at 18:30 New York on the 20th the trading day is already the 21st. The clock is injectable, so a test proves it. An explicit `start` or `end` replaces the preset.
- **The dashboard** (`api/dashboard.py`, a pure function over trade records) arranges `finance.py`'s results; no statistic is defined twice. Money leaves as cents strings, including `"0.00"` for an empty journal (never `"0"` or `"-0.00"`); ratios are plain numbers.
- Tested against a real Postgres through the request role: the numbers by hand on five trades, every filter, the preset arithmetic in two timezones, archived accounts, and two users who never see each other (including a user naming another's account ids). Two mutations (a preset from the server's date; archived always shown) are each caught.

**Slice 2 (2026-10-04): the trade log, one trade's page, the tag catalog.** `GET /api/v1/trades`, `/trades/{id}`, `/trades/{id}/neighbors` and `/tags`.

- **The log** takes the shared filters plus `q` (a case-insensitive substring of the contract, its root, the account's name or a tag's name), `sort` (`date`, `account`, `symbol`, `direction`, `qty`, `hold`, `net_pnl`; a leading `-` reverses; the default is `-date`, newest first by entry time), `limit` (1 to 200, default 50) and `offset`. It answers `{items, total, net_pnl}`: the count and the net result are for everything the filters match, not the page. Equal values are ordered by id, so paging never repeats or skips a trade. It is built in memory from the filtered trades (doc 05 section 8 measured that as cheap) and moves to SQL only if a measurement says so.
- **A trade's page** adds its fill pairs, `points`, notes, tags and screenshot records. Another user's trade and a missing one are the same 404 (row-level security hides the row). **Screenshot images are not served yet** (`src` is null; the file route is M6, with the object store), the records are real.
- **Neighbors** reuse the log's filters, search and order, so the arrows on a trade's page follow the list the person came from; a trade outside that list has none.
- **The tag catalog** lists groups and tags, each tag with its trade count (the tags page will need it).
- Tested on the real sample export (8 trades from 14 fill pairs, some scaled in or out): paging covers every trade once, each of the seven sorts and its exact reverse, search and the totals that follow it, the journal flags, the 404s, isolation. Three mutations (search ignoring tags, the total counting only the page, the sort direction ignored) are each caught.

**Slice 3 (2026-10-04): the real account service and a development sign-in.** `PgAccountService` (`api/pg_services.py`) implements `load` and `update_settings` on Postgres, so `GET /api/v1/session` and `PATCH /api/v1/settings` work against the real database; it is what M5 reuses behind real sessions.

- **Who the user is** comes through the `login` system role (the request role cannot read the `users` table; a suspended user or one being deleted is "not signed in"); **their settings** come through a tenant session. `ApiConfig` gains `TJ_LOGIN_DATABASE_URL`.
- **Changing the trading-day timezone or start recalculates the stored trades in the same transaction**, as the old settings page did (a trade's day depends on them). The plan is a placeholder (`free`, no entitlements) until billing (M9, M10).
- **A development sign-in** (`api/dev.py`, `TJ_DEV_USER_ID`): every request carrying one fixed cookie word is that user, so the app can run on a laptop before real sign-in exists. `ApiConfig` refuses it in production, and it still goes through the same CSRF and origin checks. `python -m tradejournal.api.devserver` starts it from the gitignored `.env.test` (no password typed or printed) as the one user in `tj_dev`; the Vite dev server sends the cookie when `TJ_DEV_API=real`. See `docs/runbooks/run-locally.md`.
- Tested against a real Postgres: load, suspended and missing users, partial updates, setting and clearing the CSV timezone, the trade recalculation (and that a theme change does not trigger it), isolation between users, and the dev server end to end including its CSRF refusal. Three mutations (suspended users signing in, no recalculation, any cookie accepted) are each caught.

**Slice 4 (2026-10-04): writing a trade's journal.** `PUT /api/v1/trades/{id}/notes`, `PUT` and `DELETE /api/v1/trades/{id}/tags/{tag_id}`, `POST /api/v1/tags`.

- **Notes** replace the trade's note and answer with what was stored (a note with no visible text, such as the editor's leftover `<p><br></p>`, is stored as empty). **Tags** go on and come off idempotently and answer with the trade's tags; **a new tag** is created in a category with the next preset colour, and the same name in any capitalization is the tag already there. Bodies refuse unknown fields (a misspelled one is a 422, not a silent no-op).
- Every change goes through the CSRF and origin checks (a `WriteTenantDep` that authenticates, checks CSRF, then needs the database); the generated deny-by-default tests covered the new routes without edits, and the new tests show a forged request changes nothing.
- **A missing row and someone else's row are the same 404**, checked up front: without it a cross-tenant tag id reaches the composite foreign key and comes back as a 500.
- **Row ids are bounded** (`1` to the bigint maximum) in paths, filters and bodies, so a huge number is a 422, not a database error. This also closes the same hole in slice 2's `GET /trades/{id}`, which a test now covers.
- **Notes are sanitized on write** (`api/sanitize.py`, 2026-10-04, with the owner's approval of the `nh3` package, version 0.3.7 checked against PyPI's published hash): only the editor's formatting survives (`p br b strong i em u s ul ol li blockquote h1-h3 a`), links keep only an http, https or mailto address and always get `rel="noopener noreferrer"`, `script` and `style` go with their contents, and a note with no visible text is empty. The front end sanitizes again on render with the same list, and a test fails if the two lists drift apart. Notes copied by the migration script are stored as they were (the golden check compares them exactly); they are cleaned on the next save and always on render.
- Tested against a real Postgres (17 tests): stored and shown on the trade and in the log, blank notes, size limit, both 404s with nothing written, tag on and off twice, the persons-own checks for trade, tag and category (including another user's), name validation in words, forged requests, oversized ids. Three mutations (tag existence unchecked, notes route without CSRF, notes never written) are each caught.

**Slice 5 (2026-10-04): accounts, rules, fees, the ledger, progress and the business totals.** `POST /api/v1/accounts`, `PUT /accounts/{id}`, `PUT /accounts/{id}/rules`, `POST /accounts/{id}/archive` and `/restore`, `GET`, `PUT` and `DELETE` on `/accounts/{id}/fees[/{root}]`, `GET`, `POST` and `DELETE` on `/accounts/{id}/ledger[/{entry}]`, `GET /api/v1/account-overviews` and `GET /api/v1/business-totals`.

- **What a change answers.** An account change answers with the account; a fee change with the whole fee schedule; deleting a ledger entry with what is left of the ledger. Fee rates read as cents ("4.00") unless they really have more ("0.625").
- **Changing a fee recalculates the account's stored trades in the same transaction**, as the old settings page did. A test pins each trade's fee to its contracts at its own rate, rounded to cents trade by trade.
- **Refusals are words.** A domain refusal ("an evaluation account ends as Passed, Failed or Closed", "give the level at which the trailing stops") is a 422 with that sentence; a missing or someone else's row is a 404 (the same); a second account with the same name in any capitalization is a 409 ("You already have an account with that name."; two people may share a name). `api/refusals.py` does the mapping once; a bug while *building* a response cannot pass for a refusal.
- **Amounts are bounded** (0 to just under a trillion; fee rates to 10,000; ledger amounts above zero) so a typo is a refusal in words and a number the column cannot hold never reaches the database. Firms are the app's list; trailing type and outcomes are the fixed words.
- **`update_rules` is new in the Postgres module**: the old app never edited rules after creation. A trailing lock needs its level, and a level without the lock is dropped, so stored rules never contradict each other.
- **Progress is worked out from closed trades only** (`api/progress.py`, pure): net result as a share of the profit target (clamped to 0 to 1) and the allowed drawdown less how far the cumulative result sits below its peak (never below zero). It is an estimate, as the page already says: an intraday trailing drawdown depends on open-trade highs an export does not contain, and the trailing type and lock level are stored but not part of the arithmetic (the full rule tracker is after the beta, note A).
- **Business totals**: costs, payouts and their net, the evaluation pass rate (closed evaluations and funded accounts do not count) and the accounts with no cost recorded (a payout is not a cost).
- Tested against a real Postgres (41 tests) and on plain records (6): every refusal above, the type change reclassifying trades, rules consistency, archive and restore, fees with recalculation, the ledger order and deletion, progress cross-checked against the dashboard's own drawdown series, totals, and another person's account refused on every route with nothing changed. Three mutations (no recalculation on a fee change, a lock level kept after the lock is off, duplicate names not mapped) are each caught.

**Slice 6 (2026-10-04): importing.** `POST /api/v1/imports/preview`, `POST /api/v1/imports`, `GET /api/v1/imports`, `POST /api/v1/imports/{id}/undo-preview` and `POST /api/v1/imports/{id}/undo`.

- **The preview is the real import, rolled back.** It runs the same code inside a savepoint that is rolled back (`dry_run`), so the counts always match what the real import then does (a test checks it), and nothing is written. The table of rows is built by `pg.importer.preview_rows`, which shares the "which of these does the person already have" query with the import itself (`existing_pairs`), so a row's status (`new`, `duplicate`, `other_account` with the account's name) can never disagree with the counts. This is the per-row status the importer did not report before.
- **Times are shown the way the file wrote them**: a pair's UTC instant is formatted back in the CSV timezone (the setting from slice 5b), so the wall clock in the table is the one in the person's own file, whichever zone they chose (tested in three zones).
- **A file that is not a Performance export is refused in words**: the preview answers 200 with `fatal` set (the page shows the reason), the real import a 422 with the same sentence, and nothing is written. Unusable rows are listed with their line numbers (the header is line 1). A file over 10 MB is a 413 (the request-level cap sits just above); an upload is multipart and carries the CSRF token like any change.
- **History and undo.** The history lists every import newest first, undone ones marked. Undoing shows what it will remove first (`undo-preview`, also a rolled-back run), including how many trades carried a note, tag or screenshot that would go with them; rows another import also holds stay; a second undo is a 409. Another person's account or import is a 404 on every route.
- Tested against a real Postgres (19 tests): preview equals import, row statuses across two accounts, times in three zones, the row limit, refused files, line numbers, the record and a repeat import adding nothing, undo preview then undo, shared rows surviving one undo, isolation, bad ids and missing files, the size limit, forged requests. Four mutations (the undo preview really undoing, times shown in UTC, another account's row shown as a duplicate, the preview saving) are each caught.
- Checked in a browser on a throwaway user: choose a file, see the real preview, confirm the import, see it in the history, open "Undo", see "This removes 14 fill pairs and 8 trades", confirm, see it marked Undone.

**Slice 7 (2026-10-04): managing tags.** `POST /api/v1/tag-groups`, `PUT` and `DELETE /tag-groups/{id}`, `PUT` and `DELETE /tags/{id}`, `POST /tags/{id}/merge`; `GET /api/v1/tags` now also returns the colours on offer.

- **Every change answers with the whole catalog** as it is afterwards (categories, tags with their trade counts, the nine preset colours, and the colours already on the person's tags that are not presets, to reuse), read in the same transaction as the change and built after it, so the tags screen needs no second request and a bug building the answer cannot pass for a refusal.
- **Rules**: a tag or category name is unique per person in any capitalization (a clash is a 409 in words: "There is already a tag called ORB."; a tag is unique within its category, so the same name may exist in two categories); a blank or overlong name is a 422; a colour is "#rrggbb" or "#rgb" (stored as "#aabbcc"), anything else is a 422; moving a tag to another category keeps it on its trades; merging moves every trade to the surviving tag once (a trade that had both keeps one) and refuses merging a tag into itself; deleting a tag takes it off its trades, deleting a category takes its tags and their links with it, and the trades themselves always stay.

## 11. M5 progress (running log)

Real sign-in, built in slices: the stores first, then the login flow, then the account features (export, deletion, audit viewer).

**Slice 1 (2026-10-04): sessions, invites and the audit log** (migration 0007; `pg/sessions.py`, `pg/invites.py`, `pg/users.py`, `pg/audit.py`, `api/sessions.py`).

- **Sessions** are server-side rows. The cookie holds a random 32-byte token and only its SHA-256 is stored, so a copy of the table cannot be replayed as cookies (a test searches the table's text for the token). A session ends when revoked, 90 days after it began (absolute), or after 14 idle days (the idle timer slides, written at most every five minutes); a suspended or deleting user's sessions stop at once because the lookup joins the user's status. The CSRF token derives from the row's random `public_id`, never from the cookie or the row number. "Log out everywhere" revokes all of a person's rows, optionally keeping the caller's.
- **`PgSessionStore`** (the real `ports.SessionStore`) caches a live session for 60 seconds per instance, as doc 03 says: a session revoked elsewhere stops working here within a minute and at once on the instance that revoked it; unknown tokens are never cached.
- **Invites** are stored hashed (`TJ-XXXX-XXXX` from 31 unambiguous letters and digits), may carry the one email they are for, may be used more than once, and expire or are revoked. Checking returns **one answer for every kind of failure**; redeeming takes an advisory lock per invite and rechecks inside the sign-up transaction, so two people cannot both take the last use. `python -m tradejournal.pg.invites create --label ... [--email] [--max-uses] [--days]` (as the schema owner, `TJ_OWNER_URL`) prints a code once.
- **The audit log** is append-only: the sign-in role may INSERT only, and a trigger refuses every UPDATE except detaching the history from a deleted person (the foreign keys' `SET NULL`), so even the owner cannot rewrite it; only the owner deletes (retention). Found while testing: a first draft refused that `SET NULL` too, which would have made deleting an account fail.
- **Who can touch these tables**: the request role (a person's own requests) has **no grant on any of them**; the sign-in role gets exactly what sign-in needs (it cannot rewrite whose a session is, delete sessions, or create or change invites); the sweep role may delete expired sessions and see nothing else about them. The schema lint now knows two lists of tables with a `user_id`: the tenant tables (row-level security) and these system tables, and a new table must be put on one.
- **Users at sign-in** (`pg/users.py`): find by identity-provider subject, create (active, never an operator: the column grants forbid more), and keep the email the provider reports; an email already held by another identity is refused (`EmailTaken`), in any capitalization.
- Tested against a real Postgres (30 tests, plus the lint and role suites updated): hashing, expiry and idle rules, sliding, revocation, suspension, mfa, cascades, every grant, the trigger, history outliving the account, invites in every failure and the last-use race, the CLI, the store's cache and clock. Five mutations (user status ignored, absolute expiry ignored, idle timeout ignored, invite email ignored, use-up not rechecked at redemption) are each caught.

**Slice 2 (2026-10-04): the sign-in flow** (`auth/idp.py`, `auth/kinde.py`, `auth/flow.py`, `auth/signed.py`, `api/routers/auth.py`; PyJWT with `cryptography` and `httpx` are now runtime dependencies, both approved).

- **The port and the fake.** `IdentityProvider` has three methods (`authorization_url`, `complete`, `logout_url`) and returns an `Identity` (subject, email, whether the email is verified, `acr`, `amr`, `auth_time`). The flow never sees a token. Tests use `tests/fake_idp.py`, which keeps what a real provider keeps (the `state`, `nonce` and PKCE challenge of each attempt, and single-use codes) and refuses what a real one refuses (a wrong PKCE verifier, a used code).
- **The Kinde adapter** is the only code that knows OIDC details: discovery (cached an hour, its `issuer` checked), the signing keys (cached; at most one refetch a minute when an unknown key id appears, so a stream of forged ids cannot make us hammer the provider), the code exchange with the client secret in the request body, and the ID-token check with PyJWT: **RS256 only** (no `none`, no HS256 confusion), and `exp`, `iat`, `iss`, `aud` and `sub` required, 60 seconds of clock leeway, the `nonce` compared in constant time, and `email_verified` must be exactly `true`. Step-up is `acr_values=mfa&max_age=0`, as proven in spike S1b. The adapter's own tests (22) cover every one of those; six mutations (algorithm check, audience, issuer, expiry, nonce, verified-email) are each caught.
- **`GET /auth/login?next&invite&stepup`** makes a random `state`, `nonce` and PKCE verifier, puts them (with the invite code and the `next` path) in a **signed, ten-minute `__Host-tj_login` cookie** and sends the browser to the provider. Nothing is stored on the server for an attempt that is never finished.
- **`GET /auth/callback`** checks the cookie's signature and age, the `state` (constant time), then asks the provider to complete, then records the sign-in **in one transaction**: find the person by provider subject; a new person needs a valid invite (or `TJ_SIGNUP_MODE=open`), and the account, the redemption, the session and the audit row are made together or not at all (a sign-up that loses the race for the last use is undone whole, and the invite is not spent). It then ends any session the browser still carried (a new sign-in is always a new token), sets the session cookie (`__Host-tj_session`, 90 days, Secure, HttpOnly, SameSite=Lax, Path=/, no Domain), clears the login cookie and redirects with 303. The tenant defaults (settings, usage row, three default categories) are written after commit and again on every sign-in, so a first sign-in cut short is repaired by the next.
- **Every failure looks the same to the browser**: `/invite?error=<code>` with one of `expired`, `signin_failed`, `email_unverified`, `invite_invalid`, `account_unavailable`, `email_taken`. A missing, used-up, revoked, expired or wrong-email invite is the one code `invite_invalid`; the reason goes to the audit log (`login_failed`, `meta.reason`), never to the page. Neither the code, the `state`, a token nor the secret is ever written to the log (a test searches it).
- **`next` cannot leave the site**: it must be a path starting with one slash, with no backslash, control character or second slash, not under `/auth/`, and at most 512 characters; anything else becomes `/`. It is checked when the attempt starts and again when it is read back from the cookie (two layers: removing only one of them changes nothing, removing both fails seven tests).
- **`POST /auth/logout`** (the only auth route in the OpenAPI document, so the generated CSRF tests cover it) ends the session at once (not after the 60-second cache), writes the audit row and returns `{redirect}`: the provider's logout page, so the provider's own session ends too, which then returns the browser to `/invite`, the public page (the provider must list `<origin>/invite` as an allowed logout address). Not `/`: that needs a session, so it would send the person straight to the provider's sign-in. Found while writing the runbook for the first real-tenant run, and fixed there. A cross-site page cannot sign anyone out.
- **No provider configured** (`TJ_KINDE_*` unset): `/auth/login` and `/auth/callback` answer 503 and nobody can sign in; the settings must be given all three or none, the domain must be an https address with no path, and the client secret never appears in a repr.
- **MFA**: a session records `mfa_at` only when the provider reports `acr == "mfa"` with an `auth_time`; `amr` alone does not count, and a sign-in whose MFA was two hours earlier is not "fresh" (the 15-minute window is the admin rule, M10).
- Tested against a real Postgres (24 flow tests, 22 adapter tests, 30 signing and `next` tests, 4 new config tests; 1099 backend tests pass): returning person, sign-up with an invite (typed in lower case, single use, wrong email, revoked, junk, none), open mode, the race, unverified email, suspended user, an email that belongs to someone else, MFA fresh, stale and `amr` only, wrong or missing `state`, replay, edited cookie, nonce or PKCE mismatch, provider error, a network failure, seven kinds of hostile `next`, cookie flags, `Cache-Control: no-store`, rotation, logout with the CSRF cases, one session's token refused on another, and no provider. One honest note: removing only the first `next` check survives, by design, because the second still protects the redirect.

**Slice 5 (2026-10-04): export of all your data** (`pg/export.py`, `api/routers/export.py`; requirement F-A5, a P0 launch item).

Those need the file store (M6) and an email provider, neither of which exists, and a journal this size does not need them. A test puts another person's account, trade note and day note in the database and searches every byte of the file for them.
- **Streamed.** Rows come through server-side cursors in batches of 2,000 into the ZIP, held in a spooled file (memory to 16 MB, then disk), so a long history never has to fit in memory (a test reads 4,000 trades in batches of 300 into a file forced onto disk). The file is byte-for-byte the same for the same data and moment.

The plain-text version turns paragraphs and list items into lines and entities back into characters.

**Slice 8 (2026-10-04): rate limits** (`api/ratelimit.py`; doc 04 T2, T5, T18).

- A **token bucket per rule and key**: a rule says how many requests are allowed in a burst and how fast the allowance comes back. Taking a place is O(1), the table is bounded (the oldest keys are dropped first, so a flood of different keys cannot grow memory), and the clock is injectable. A refusal is a `429` problem document ("Too many requests. Try again in 20 seconds.", rounded up, in seconds, minutes or hours) with a `Retry-After` header; the refused request does not run, write, or audit anything.
- **Who is counted.** Behind a session, the *person*: everything they do (600 requests a minute, a safety net, not a plan limit), exports (5 an hour: an export reads every table), import previews (60 an hour) and imports (30 an hour), each with its own allowance. Anonymous and bad-cookie requests are turned away with 401 *before* anything is counted, so a stranger can never use up a person's allowance. Before sign-in, the *client address*: starting a sign-in (30 a minute), the way back from the provider (30 a minute), and a separate, stricter limit on sign-in attempts that carry an invite code (10 per 15 minutes), since guessing codes is the one thing worth its own limit (a plain sign-in does not count against it).
- **The client address** is the socket's unless the host names a header (`TJ_CLIENT_IP_HEADER`, for example `CF-Connecting-IP` behind Cloudflare). Name one only if every request comes through a proxy that sets it, otherwise a caller could pick their own address and so their own bucket; with none named, a spoofed header is ignored (tested). Values are bounded to 64 characters.
- **Per process, on purpose.** Two instances give a person twice the allowance; this is a brake on abuse and accidents, not a meter. Doc 02 moves it to Postgres or Redis when load needs that, and Cloudflare's own rules sit in front for floods (set them at deploy time, S4). `TJ_RATE_LIMITS=off` switches it off for development or an emergency.
- Tested: 30 limiter tests (bursts, refill, caps, isolation, bounded table, 300 threads getting exactly the allowance, a clock that goes backwards, wait wording, address rules), 8 on the app (per person, strangers cost nothing, the refused change never ran, the off switch, configuration), 8 on Postgres (export, previews and imports separately, sign-in per address with and without a configured header, invite guesses counted apart, the callback, and a normal person nowhere near the limits). Nineteen mutations are each caught (one needed a changed test: a backwards clock must not lock anyone out). Every operation in the OpenAPI document now lists the `429`.

**Slice 9 (2026-10-04): deleting your account** (migration 0008; `pg/deletion.py`, `pg/sweep.py`, `auth/kinde_admin.py`, `api/routers/account.py`; requirement F-A6, a P0 launch item).

- **Asking is deliberate in three ways.** `POST /api/v1/account/deletion` takes `{email}` and needs a session, the CSRF token, **a sign-in at the identity provider within the last ten minutes**, and the account's own email address typed out. Not recent: `403` "Sign in again first". Another address: `422`. An account that cannot be scheduled (suspended, or already pending): `409`. On success the account becomes `pending_deletion` with `deletion_scheduled_at = now + 7 days`, **every session of the person ends (this one too) and the cookie is cleared**, and the answer is `{scheduled_for}`. The request and the audit row (`deletion_requested`) are one transaction.
- **"Signed in a moment ago" is checked, not trusted.** The page sends the person to `/auth/login?reauth=1&next=...`, which asks Kinde for `prompt=login&max_age=0` (the password or factor again, whatever the provider's own session says). The callback does not take the provider's word that it asked: it checks the ID token's `auth_time` is within two minutes and not more than a minute in the future, that the answer is for **the same person** as the session that asked, and that there is a session to begin with. Any miss is `/invite?error=reauth_failed` with the reason in the audit log. The new `sessions.authenticated_at` records the provider's own `auth_time` (never later than now), because a provider can sign someone in silently from a session days old: "recent" is judged on that, not on when our session began. `GET /api/v1/session` says it as `flags.recently_authenticated`.
- **Changing your mind is signing in.** A pending account that signs in during the week goes back to `active` (`deletion_cancelled` in the log) and lands on `/settings/privacy?restored=1`, which says nothing was deleted. There is no cancel route: no session exists while it is pending, and sign-in is the one thing that can make one. (Doc 07 listed a `DELETE /account/deletion`; it is not needed.)
- **The database keeps the rules, not only the code.** A constraint ties a date to the status (`pending_deletion` always has one, nothing else does). The sign-in role may not write `users.status` (a suspended person must never be able to un-suspend themselves through a bug in sign-in), so it calls two narrow `SECURITY DEFINER` functions with a fixed `search_path`: one moves **active** to pending, the other **pending** back to active, and nothing else. The request role cannot call them or see the date; a test tries a `search_path` trick against them.
- **The sweep** (`python -m tradejournal.pg.sweep deletions [--apply]`, as the `sweep` role, `TJ_SWEEP_DATABASE_URL`) is a **dry run unless `--apply`**, and **must run as a scheduled job on the host** (hourly is plenty; nothing deletes an account until it does). The role can see `idp_subject` and the date of a person and nothing else (not the email), delete what is due, and write the audit log. For each due account, in one transaction: the audit row, the `DELETE` (whose own `WHERE` re-checks "still pending and due", so a person who signed in a moment ago is not deleted; a test proves that check holds even with the constraint removed), and the identity's id into the **outbox table `identity_removals`**. Cascades remove every tenant row in every table, the person's invite redemptions and sessions; the audit history stays, detached from them. Then, separately and repeatably, each recorded identity is removed at Kinde (the Management API, with a machine-to-machine application: `TJ_KINDE_M2M_CLIENT_ID` and `TJ_KINDE_M2M_CLIENT_SECRET`, plus `TJ_KINDE_DOMAIN`) and forgotten once Kinde confirms; a failure keeps the entry, with `attempts` and the reason, for the next run. **An identity is never left that nobody remembers.** Without a provider configured `--apply` refuses, unless `--without-identity-provider` says so (local development). It prints counts, never an email or an id.
- **Not done yet, on purpose.** The screenshot files (the R2 prefix) do not exist until M6, and the subscription cancel arrives with billing (M9); each of them has to be added to the sweep, in front of the row delete, when it lands. The tombstone doc 03 describes (a hashed email for billing reconciliation and abuse control) waits for billing too. The Privacy Policy must say backups age out within their retention window.
- Front end: Settings > Data & privacy has a **Delete my account** card and a dialog that says exactly what happens (permanently deleted 7 days from now, signed out everywhere straight away, sign in again before then and nothing is lost, a link to download first). If the person did not sign in a moment ago the dialog says so and offers **Sign in again**, which comes back to the page with the dialog open (`?delete=1`, removed from the address when it closes). Otherwise they type their email address; the red button stays off until it matches (capitals and spaces do not matter), and **what they typed is what is sent**, so the server is the one that compares. The dialog cannot be closed or sent twice while the request is out, a refusal is shown as the server's sentence, and success goes to `/invite?deleted=<date>`, which says "scheduled for deletion on Oct 11, 2026" and that signing in again undoes it (only a plain ISO time is ever turned into that sentence).
- Tested: **90 backend tests** for deletion (27 on the rules and grants against Postgres, 15 on the sweep, 16 on the sign-in flow's re-authentication and restore, 12 on the route with no database, 20 on the Kinde Management client over a mock transport), plus the sign-in, session and OpenAPI tests updated for the new column, flag and route (1301 in all passed before the rebase onto the rate limits). ## 12. Plans and plan codes (M9 and M10 groundwork, running log)

**Slice 1 (2026-10-04): the effective plan, plan codes and the redeem route** (migration 0010; `entitlements.py`, `pg/plans.py`, `api/routers/grants.py`; doc 03 section 5, ADR-012). Nothing here needs the payment account or the admin screens, so it is built first.

- **The rule** (`entitlements.effective_plan`, plain values in and out, no database): an active **override** wins outright, even when it lowers the plan; otherwise the **higher** of an active **grant** and a live **subscription** (active, trialing or in grace, period not ended), with the subscription as the source on a tie because it is the one that renews; otherwise **free**. Never stored, so billing cannot overwrite an operator's decision. The subscription mirror table comes with billing (M9); the function already takes it.
- **What a plan includes is empty on purpose.** `LIMITS` has an entry per plan, both empty: what Free and Pro limit (accounts, history, files) is a business decision nobody has made, and nothing here invents it. A limit added later is one line, and the Plan page already lists whatever the session carries. **A decision for the owner:** what should Free include, and what should Pro add?
- **Tables** (none under tenant row-level security; the request role has no grant on any): `grant_codes` (hashed, plan, days 1 to 3650, optional limit on uses, optional expiry, revocable), `grant_redemptions` (one per person per code), `plan_overrides` (required reason, at most one active per person by a partial unique index, history kept), and `invites.grant_code_id`. Rows belonging to an account go with it when it is deleted; a code and other people's redemptions stay. The sign-in role reads codes by hash, reads what decides a plan, and records a redemption; it cannot make, change or revoke a code or an override, and cannot see an override's reason or who made it.
- **`POST /api/v1/grants/redeem`** (`{code}`; session and CSRF token; 10 tries an hour per person, right or wrong): the code is tidied like an invite code, then **one answer for every code that does not work** (wrong, used up, expired, revoked, already used by this person: a 422 with one sentence), so a guess teaches nothing, and a bad code is refused even to someone who already has a plan, so that cannot be probed either. A valid code for someone who already has a plan from a code that has not ended is a 409 that says until when (one at a time; a simple rule chosen in the design). Redeeming takes an advisory lock on the code, so two people cannot both take the last use. The audit log gets `grant_redeemed` (plan, days, how) or `grant_refused` (why), never the code.
- **An invite can carry a plan** (`invites create --grant-id N`): "90 days of Pro for testers" is given inside the sign-up transaction. A code that ran out or was revoked meanwhile gives nothing, and the sign-up still goes ahead.
- **The owner's command** (until the admin screens, M10): `python -m tradejournal.pg.plans create-grant --label ... --days 90 [--max-redemptions N] [--expires-days N]` prints the code once (`GR-XXXX-XXXX`, its own prefix so it is not mistaken for an invite), `list-grants` shows each code's use without ever showing a code, and `revoke-grant --id N` stops one (people who used it keep their plan).
- **Front end:** Settings > Plan & billing has a **Have a plan code?** card under what the plan includes: a box, a Redeem button that stays off until something is typed, the server's own sentence on a refusal (the box keeps what was typed), "Done. You are on the pro plan until Jan 12, 2027." on success, after which the session is read again so the page shows the new plan and where it came from.

## 13. Observability (M7 groundwork, running log)

**Slice 1 (2026-10-04): structured, scrubbed logs and request ids** (`api/logs.py`, `api/requestlog.py`, `api/errors.py`, `api/app.py`, the Dockerfile; doc 04 section 5, finding S12). Until now the API wrote nothing of its own: the server printed an access line for every request, query string included (so the sign-in callback's one-time `code` and `state` went to the log), and an unhandled error's traceback carried its message (which, for a database error, can quote the value that broke a constraint, such as an email or a note). Neither is acceptable for a product that holds other people's trading journals. Nothing here adds a dependency.

- **Production writes JSON, one line per record** (when, level, logger, message, request id, named facts), to standard output, switched on when the app starts with `TJ_ENV=production`. Development and the tests keep Python's quiet default, so a local run is unchanged.
- **A scrubber on everything written** (`logs.scrub`, applied to every message and every text fact): the value of any `name=value` whose name contains code, state, token, secret, password, key, authorization, cookie, session, csrf, nonce or verifier; bearer and basic credentials; JWTs; hexadecimal runs of 32 or more characters (a session secret, a CSRF token, a hash); the password in a connection URL; and email addresses. The patterns lean eager: a readable line may lose a word, a leak is worse.
- **An error is its kind and its place, never its message** (`logs.error_summary`): the exception's type, the database error code and the table and constraint names when it has them, the types it was raised from (up to three), and the file, line and function of the last twelve frames. This replaces the standard traceback for every record, including the server's own `uvicorn.error`.
- **The request line** (`RequestLogMiddleware`, outermost, so a refusal by another layer, such as a 413, is logged too): the method, the route's template (`/api/admin/v1/invites/{invite_id}/revoke`, so ids do not make every line different; a path nothing matched is written as it came, scrubbed and then cut to 200 characters, in that order so a cut cannot leave half an address), the status, and the time. **Nothing else about the request**: not the query string, headers, cookies, body, user agent or client address. 5xx is an error, 4xx a warning, the rest info; the health checks and the built assets are written only when they fail.
- **A request id** (`X-Request-ID`): the caller's when it is 8 to 64 letters, digits, dots, dashes or underscores (so the edge can supply one and a support request can quote it), otherwise a random UUID. It is returned on every answer including a 500 (the 500 handler runs outside the middleware, so the id is left on the request for it), and every other record written while the request runs carries it.
- **The page shows the reference** (`lib/api/client.ts`): a server failure that has no sentence of its own (a 500 or 503) now reads "The server had a problem. Try again in a moment. If it keeps happening, tell us this reference: `<id>`." The id is the response's `X-Request-ID`, and is shown only when it is a short plain token (8 to 64 letters, digits, dots, dashes or underscores), so nothing odd from a header can reach a page. A server's own sentence (such as the operator tools' "not set up") and refusals (4xx) are unchanged. The operator searches the log for the id to find that request and everything else written while it ran. 4 new front-end tests (837 in all); 10 mutations are each caught.
- **The server's own noise is turned off**: its access log (`--no-access-log` in the container, and its logger is cut off in the process), its handlers (they would print plain text beside ours), and the HTTP client libraries' INFO lines (each outgoing address, with its query string).
- Tested: **82 tests** (the scrubber on every pattern and the boundary of the hexadecimal rule; each part of an error summary; the JSON line; configuring twice; the servers' loggers; the request line's fields, levels for nine statuses, ids from the caller and their limits, the id on a 500, on a 413 from an inner layer and on a failure after the answer began; and the one that matters most, which sends a secret in the query string, the cookie, the authorization header, the user agent, a header and the body, and reads the whole output for any of them). **Fifty-five of fifty-six mutations** are each caught; the other (swapping the order of the request log and the security headers, neither of which can refuse anything) is equivalent. The first mutation run left two survivors. One was that scrubbing a path in the middleware was redundant with the formatter's scrub, which showed the real defect: cutting a path before scrubbing it can leave half an address that no pattern recognises, so the middleware now scrubs and then cuts, and a test puts an address across the cut. The other was a swap of two middleware that cannot refuse anything (equivalent); a mutation that put the request log inside the body limit was added and is caught by the 413 test.
- **Found while writing it:** the HTTP test client's own library was writing the request URL, query string included, through the new handler; that is how the quieting of the client libraries came about.
- Not here: Sentry or another error tracker (it needs an account, a dependency and its own scrubbing set to match: the owner's yes, and then it is a small change on top of `error_summary`); a user id on the request line (it would make a line identify a person; the audit log is where that belongs); alerts on the log (they need a host to run on); and log shipping and retention (the host's).

## 14. Hardening (launch gates, running log)

**Slice 1 (2026-10-04): the CSV row cap and the import concurrency limit** (`parser.py`, `api/slots.py`, `api/deps.py`, `api/routers/imports.py`, `api/config.py`; doc 04 T3, T5 and S7). Two parts of one launch gate that need nothing from the owner.

- **A file may have at most 50,000 data lines** (`parser.MAX_ROWS`; the figure doc 04 suggested). It is checked before the file is parsed, after the header (so a file of the wrong kind still gets the more useful "not a Tradovate Performance export"), and counts every line, blank ones too, because they are all read. The 10 MB upload cap alone would still let a file of very short rows through; every row is held in memory. The refusal comes back as the importer's `fatal` ("That file has 50,001 rows, and one import takes at most 50,000. Export a shorter period (by month, say) and import the parts one at a time."), so the preview, the import (a 422) and the command line all show it the way they show any refused file, and no front-end change was needed.
- **At most two imports run at once in a process, and a person runs one at a time** (`ImportSlots`, `TJ_MAX_CONCURRENT_IMPORTS`, 1 to 16, default 2). Reading a file and regrouping a journal holds a worker thread and the processor for a second or more; without a limit a few people importing together, or one person pressing the button forty times, could take every thread the server has. A request that cannot have a place is **refused at once with a 429 and `Retry-After: 5`**, not queued (a queue of waiting requests is the same thread problem in another place), with one of two sentences: "You already have an import running..." or "Imports are busy right now. Try again in a few seconds." The place is given back however the request ends, and a stranger is refused (401) before one is taken. It applies to preview, import, undo preview and undo, the four routes that do the heavy work, and is independent of the rate-limit switch (`TJ_RATE_LIMITS=off` is for a limit that is wrongly refusing people; this protects the process). The count is per process; the database's per-user advisory lock still orders one person's imports across instances.
- Tested: 9 parser tests (the real limit at 50,000 and 50,001 with the three kinds of line ending, a last line with no newline, the header first, a small limit on real rows) and 27 on the slots (the unit, a crowd of 200, a set that sleeps while it counts so a missing lock shows up, the dependency through the real app with a route that blocks, the four routes by reading the routers, the configuration). **32 of 33 mutations** are each caught; the other is equivalent. A first run left the missing-lock mutation alive, because a race that rare does not show on its own; the sleeping set makes it certain.
- Not here: the pixel cap (screenshots, M6), the edge cap (deploy), per-route exact limits for screenshots (M6), and a front-end message for the 429 (the page already shows the server's sentence for any refusal).

**Slice 2 (2026-10-04): import and undo are audit events, and the launch checklist is brought up to date** (`api/routers/imports.py`, `lib/admin.ts`; doc 04 sections 4 and 5). The checklist said "audit log events written (login, failure, change, import, undo, export, delete, admin)" and import and undo were the two that were not. **Slice 3 (2026-10-04): database timeouts** (`pg/session.py`, `pg/system.py`, `api/errors.py`, `api/deps.py`; doc 04 T5 "request timeouts", and the new row in its gates table). Found by reading the pool setup while looking for what a load would break: a request waited **30 seconds** for a free connection (psycopg's default, with a pool of 10 behind 40 worker threads), a query could run for as long as it liked, and a per-person advisory lock could be waited on for ever. Each of those holds a worker thread, and enough of them leave nothing for anyone else's page.

- **Every tenant transaction** now carries a statement timeout (15 seconds) and a lock timeout (5 seconds) as transaction-local settings, set in the same statement as the tenant, so neither can leak to the next user of a pooled connection (a test reuses a pool of one to show it); the pool waits 5 seconds. **The routes that touch every row a person has get 2 minutes per statement** (`HEAVY`): import, import preview, undo, undo preview, the export, a fee change (it recalculates the account's trades) and a settings change that moves the trading day. The local-journal migration uses the long limit too. The system roles have limits of their own: sign-in and billing 10 seconds, the operator tools 15, the deletion sweep 5 minutes, and a 5-second pool wait.
- **Three errors are now answers, not 500s**: running out of pool (`PoolTimeout`), a cancelled statement (`QueryCanceled`) and a lock wait (`LockNotAvailable`) become a **503 with `Retry-After`** and one sentence each in words ("The server is busy right now. Try again in a few seconds."; "That took too long and was stopped. Try again in a moment, or ask for less at once (a shorter period, fewer filters)."; "Your journal is being changed by something else. Try again in a few seconds."). The front end already shows the server's sentence for a refusal. The handler writes one log record with the error (its type and database error code, never its message), because the request line says only "503".
- Tested: 23 Postgres tests (the values; the settings seen from inside a session, ordinary, heavy and snapshot; a `pg_sleep` cancelled on time and not before; the settings gone from the connection afterwards; a lock wait that ends; the pool of one that gives up on time and works again; each system role's limit; the three answers through the real app, with what the log keeps; a different database error still a plain 500 that leaks nothing; and which routes get the long limit, by spying on the sessions they open). **35 mutations** are each caught; the first run left one alive (the lock timeout following the connection), because the leak test looked only at the statement timeout.
- Not here: a limit on a whole request (a request of many fast statements is bounded by the import limits and the rate limits), and the pool size as a setting (10 per process; it becomes one when the host's plan is known). The pool and its limits have not been load tested.

**Slice 4 (2026-10-04): screenshots, the first half** (`images.py`, `filestore.py`, `pg/screenshots.py`, `api/routers/screenshots.py`, migration 0012, `api/deps.py`, `api/config.py`; doc 03 section 6, doc 04 T3). The routes, the stores and the checks for the pictures a person attaches to a trade, and the page connected to them. What is **not** here is on purpose and listed at the end.

- **What is accepted.** One image per request (`POST /api/v1/trades/{id}/screenshots`, multipart): a **PNG, JPEG, GIF or WebP**, up to **10 MB**, **50 million pixels** and **20,000 on a side**. The kind and the size come from the file's own header (`images.inspect`, no library): a few hundred bytes can claim 100,000 pixels on a side, and whoever opens the file pays for decoding it, so the picture is capped by pixels and not only by bytes. The type the browser declares and the name the person gave decide nothing: the file is stored and served under the type its header gave. **SVG is never accepted** (it can carry script). Each refusal is a sentence in words ("That is not a PNG, JPEG, GIF or WebP image."; "That image is 65,535 by 65,535 pixels, which is more than the 50 million pixels (or 20,000 on a side) a screenshot may have. Take a smaller one.").
- **Where the bytes live.** Behind a five-method interface (`FileStore`: put, get, delete, delete a prefix, list), with one store today, `LocalFileStore`: a folder (`TJ_FILES_DIR`), which is what a development machine and a host with a persistent disk need. The design's production store, a private bucket (Cloudflare R2), is a second class with the same methods, chosen in `api/app.py`; nothing above the interface changes. Keys are made by the server (`u/<user id>/<random>.<ext>`, at most 120 characters of `a-z 0-9 . _ - /`, no `..`), never by a request; a write goes to a temporary file in the same folder and is renamed into place, so a reader never sees half a file; and the folder refuses any key that resolves outside it, links included. **With no `TJ_FILES_DIR` the screenshot routes answer 503** "Screenshots are not set up on this server yet." and a trade's screenshots carry no address, rather than losing an upload.
- **The database and the files agree.** `add` checks everything first (size, header, the trade, the limits), writes the file, then inserts the row and, if the insert fails, removes the file again. `delete` removes the row inside the transaction and the route removes the file only after the commit, because a rolled-back delete must not have lost the file. A crash between the two leaves a file with no row; the orphan job (below) reports those. Migration 0012 adds the type, size, width and height to `screenshots`; the size is summed into `user_usage.storage_bytes` (the operator's counters and, later, a quota are one number). A row from before the migration is served by the end of its name and counts as 0 bytes.
- **Limits** (constants for now; what a plan includes is the owner's decision, so `entitlements.LIMITS` stays empty): **20 screenshots per trade** and **500 MB per person**, each refused with a sentence that says what to do ("A trade can have 20 screenshots at most. Delete one to add another."; "That would take you over your 500 MB of screenshot space. Delete some you no longer need to make room."). The count and the sum are read under the per-person advisory lock, so uploads arriving together cannot all slip under the same limit. **120 uploads an hour per person** (rate limit), and the 12 MB multipart ceiling from the request limits still applies.
- **Serving** (`GET /files/{id}`): a plain GET (the session cookie rides along on an `<img>`; a safe method needs no CSRF token), loaded under row-level security, so another person's id is the **same 404** as a missing one. The answer carries the file's own type, `X-Content-Type-Options: nosniff`, `Cache-Control: no-store` (every `/files/` answer is per person) and a `Content-Disposition` built from the id and the stored extension, never from the name the uploader chose. A row whose file has gone missing is a 404 in words, not a 500. Deleting (`DELETE /api/v1/trades/{id}/screenshots/{id}`) answers with the screenshots that are left; a screenshot named under the wrong trade is a 404.
- **The page.** `apiSource.addScreenshots` and `deleteScreenshot` were the last two calls that said "not connected"; they are real now. A drop of several images goes **one request at a time** (each is checked and answered for on its own, and each stays under the size limit), stops at the first refusal, names the file when there were several, and says how many were kept before it ("b.png: That is not a PNG, JPEG, GIF or WebP image. 2 images added before it."); the page reads the trade again after a refusal as well as a success, so the ones that were kept appear.
- **Tested.** 101 unit tests for the header reader (real headers of each format, every truncation of a PNG header, a tiny file claiming a huge picture, the markers a JPEG may carry, headers that look right but are not) and 43 for the store (keys that try to escape, atomic writes, prefixes, listing); 42 on Postgres for the domain functions and the routes (what is stored under what key, the counters, every refusal and its sentence, the limits at and one over, a failure while recording taking the file out again, a store whose `put` makes uploads meet so a missing lock shows up, another person's id on every route, a store that is not there); the generated two-tenant suite (97 tests, 8 more) now gives each person a screenshot, attacks the two new routes with the other's ids and also checks that **the folder of files is unchanged** by every attack, and a separate test fetches the image as the other person; one test that `storage_bytes` is the sum of the sizes on record; and 9 on the front end's source and the page. **74 mutations of the backend and 17 of the front end** were tried: 13 of the backend ones survived the first time (a boundary on the tall side, the PNG header's chunk name and length, a truncated header, the markers that carry no length, a scan before a frame, the VP8 start code, two dots inside a key name, the missing lock) and each now has a test that fails without it. **Slice 5 (2026-10-04): screenshots follow the person: the export carries the image files, and deleting an account deletes them** (`pg/export.py`, `pg/sweep.py`, migration 0013, `api/routers/export.py`, the Data & privacy page; requirements F-A5 and F-A6, doc 04 "Export and deletion work end to end").

- **Export.** The ZIP now holds `screenshots/<id>.<ext>`, named by the `id` column of `screenshots.csv` (the stored name is internal and still not exported). Each file is copied as stored and **not compressed again** (an image already is), is listed in the manifest with its size and SHA-256 like every other file, and comes only from the signed-in person's own rows (row-level security decides which rows the export can see, and the store is asked only for their keys). **A gap is never silent:** a row whose file cannot be found (one made before the files were kept here, or lost since) is left out of the folder and its id is listed in `manifest.screenshot_files.missing`, and a server with no file store says `included: false`. A file is named by a picture extension or `.bin`, never by one that could do something when opened (`.svg`, `.html`). The audit event gains a count (`screenshots`), never a name. The export route passes the app's store; the same ZIP with the same data and moment is still byte for byte the same.
- **Deletion.** The sweep now writes the person's folder (`u/<user id>/`) into a new system table, `file_removals` (migration 0013), **in the same transaction that deletes the account**, and afterwards removes it from the file store and forgets the entry once the store confirms: the same shape as the identity outbox, for the same reason (a failure must not leave files nobody remembers). A person who signs in at the last moment is rolled back whole, files included. A store that fails leaves the entry, counts the attempt and keeps **the kind of error only** (a message could hold a path); one failing folder does not stop the others; with no store configured on the job the entries wait and the run says so on stderr. The table has no `user_id` column (it outlives the account, and a folder named by a former user's random id names no one), only the sweep role may touch it (insert, read, delete, and update the two retry columns), and a CHECK allows only `u/<a uuid>/`. The command prints counts only (`file folders removed N, file folders still to remove M`). **On a host the sweep job must see the same disk as the web server** (`TJ_FILES_DIR`); `docs/runbooks/run-locally.md` says so.
- **Pages.** Data & privacy says the screenshots come with the download and that the manifest names any file that could not be found; the delete dialog lists screenshots among what is deleted.
- **Tested.** 11 new export tests and 2 on the route (byte for byte, named by id, uncompressed, only your own, a missing file named, a stored name that is not a key or ends in `.svg`, no store, none at all, the same bytes twice), 12 new sweep tests (a person's files go and nobody else's, a dry run, a failing store with a path in its message, one failing folder, no store, a person who signs in in between, a folder already gone, three kinds of store error, the command's counts and its stderr note) and 9 on the new table's privileges and its CHECK. **28 mutations** of the new code are each caught. A first pass could not apply six of them because the files they edit have Windows line endings; the runner now handles both, and a lower-casing of the extension turned out to be dead code (a key is always lower case) and was removed.
- **Not here:** the **orphan job** (files with no row, such as a crash between writing a file and its row; it needs a way for a system role to list every screenshot key without reading anything else, so it is its own slice and its own design note), the migration of the **real journal's 14 image files** into the store (slice 6, below), Pillow, thumbnails and R2.

**Slice 6 (2026-10-04): the journal migration takes the image files in too** (`pg/migrate_local.py`, `docs/runbooks/migrate-local-data.md`). Until now the migration copied screenshot *rows* with their old file names and left the files for "the R2 pipeline", so a migrated journal would have shown pictures that could not be opened and an export that listed every one as missing.

- **With a file store** (`--files-dir`, or `TJ_FILES_DIR`) each screenshot's file is checked **the way an upload is** (a real PNG, JPEG, GIF or WebP by its header, 10 MB, 50 million pixels, 20 per trade, 500 MB in all), copied under a new key in the person's own folder (`u/<user id>/<random>.<ext>`), and its row records the key, type, size and dimensions (so the person's storage counter is right). A file that is **missing, not an acceptable image, or over a limit is not copied**: its row still is, under its old name, and the report says which and why (the first reason wins; the export lists such a row as missing). A stored name with a folder in it is never opened (a journal file is only a copy of the person's own, but the reader should not be able to be pointed elsewhere). **Without a store** only the rows are copied and the report says so in a sentence.
- **The golden check grows two parts.** The screenshot rows are compared with the old names mapped to the new keys, so a row pointing at the wrong file fails; and **every copied file is read back from the store and its SHA-256 compared with the original's** (a file that arrives changed, or never arrives, fails the run). A **dry run** checks every file and writes none (and so has no read-back to make); a failure after files were put **takes them out again**, because the rows are rolled back with the transaction and nothing may be left behind.
- **Rehearsed on the real journal (2026-10-04), as a dry run, as a throwaway user in the local database:** all **14 of 14** screenshot files would be accepted (1,541,430 bytes), every golden check passed, and nothing was written. (That run first brought the local development database from migration 0007 to 0013, which only adds schema.) The real run still waits for the owner's yes and for sign-in.
- **Tested.** 23 new migration tests (2,270 in the backend in all): every file in and read back with the same bytes (type, extension, width and height from the header, the counter), a dry run that writes none, a file that is not an image (the old test bytes claim 0 by 0), a file over 10 MB and one of exactly 10 MB, a file that is missing, the per-trade and per-person limits and filling the space exactly, the first refusal reason winning, a folder in a stored name, a failure that takes the files out again, a changed file, a file that never arrived and a wrong key (each turns a check red), each kind of image keeping its own extension, no store, each person's own folder, an export of a migrated journal with no missing file, and the command with the folder from the option and from the environment. **32 mutations** of the new code are each caught (two survived at first: the order in which refusal reasons are decided).

**Slice 7 (2026-10-05): the bucket as a file store** (`bucketstore.py`, `api/config.py`, `api/app.py`, `api/errors.py`, `pg/sweep.py`, `pg/migrate_local.py`, `pg/screenshots.py`; doc 03 section 6; `docs/runbooks/deploy.md`). The second implementation of the five-method `FileStore`, for a host with no persistent disk and for the deletion sweep, which runs as a **separate scheduled process** and so cannot share a web server's disk (on Render a cron job cannot attach the web service's disk, which would have left deleted people's pictures behind). **Written, tested and not yet run against a real bucket**: that needs the owner's R2 bucket and token (spike S3).

- **No new dependency.** Requests are signed with AWS Signature Version 4, which is a page of arithmetic (`hmac`, `hashlib`), and sent with `http.client`. A client library would be code that holds the secret key on every request and a supply-chain entry to approve; the signature is checked against **the worked examples AWS publishes** (GET with a range, PUT with a dollar sign and a payload hash, a bare query name, a sorted listing query), so a mistake in it cannot hide behind a fake server that makes the same mistake.
- **Settings.** `TJ_S3_ENDPOINT`, `TJ_S3_BUCKET`, `TJ_S3_ACCESS_KEY_ID`, `TJ_S3_SECRET_ACCESS_KEY` (all four or none; `TJ_S3_REGION` defaults to `auto`, R2's name for "wherever"). Every one is checked (an endpoint with a path, a bucket name that is not one, a secret with a space or a line break in it) with a message that names the setting and never its value; production refuses a plain `http` endpoint; a folder and a bucket together are refused; the secret is not in any `repr`. The web service, the sweep command and the journal migration command all choose the store from the same settings.
- **Behaviour that matters.** A request is tried **three times** with a growing pause when the network or the bucket fails (a 5xx, a 429, a dropped connection, a timeout) and **once** when it says no (bad credentials: retrying would only lock us out faster). An error is `StoreUnavailable` (an `OSError`), never carrying the answer, the address or the keys; the API turns it into a **503 in words with `Retry-After: 10`** ("Saving and showing pictures is not working right now"), and the log gets the kind only. **A 404 is "that file is gone" only when the answer's code is `NoSuchKey`**: a wrong bucket name (`NoSuchBucket`) is an error, so it can neither make every picture look deleted nor make a deletion look done (the sweep would stop retrying for ever). Deleting a prefix refuses an empty one *before* listing, because "list everything" is what an empty prefix means to a bucket (a test found that the first version would have emptied it). Pictures are never linked to the bucket: `GET /files/{id}` reads them through the server.
- **Two things found in the existing code and fixed.** A delete the person asked for no longer turns into an error when the file's removal fails after the database delete has committed (they would have retried into a 404): the row is gone, the file is left for the orphan report, and the failure is logged. And the upload's cleanup now also covers the usage-counter step, so a failure there no longer leaves a file behind with no row, and a store that is down while it tidies up no longer hides the real error.
- **Tested.** 11 tests of the signature, 76 of the store itself (the same contract run against the folder store and the bucket store, so the two cannot drift: a round trip of 256 KB and of 5 MB, an empty file, replace, missing, delete, a prefix that is not a longer id, listing with sizes and UTC times and **pages** whose tokens contain slashes and equals signs, keys the server would never make refused before any request, a wrong secret, an unknown key, a wrong bucket, a clock two hours off, retries and their pauses, a dropped connection, a timeout, an unreachable server whose message names no address, and every setting), 13 on choosing the store, and 16 on Postgres (an upload lands under the person's folder and comes back through the server; a bucket that is down refuses an upload and a picture in words and keeps nothing; the delete case above; the sweep command removing one person's objects and no one else's, and finishing the job on the next run after a failure; the migration command copying into a bucket, checking each file against its checksum, and a dry run leaving it empty). The fake server (`tests/fake_s3.py`) verifies what a real bucket verifies: the signature recomputed from the request as it arrived, the payload hash, the clock and the host. The backend now has 2,505 tests. **38 mutations** of the new code were tried; 35 are caught and three do the same thing as the original (Python's URL quoting already leaves the characters the second argument names alone, the upload's content-type header is not signed, and the secret is already hidden by the settings' own `repr`).
- **Not here:** the orphan report (listing keys that no row names needs a system role that can read every person's keys, which is the opposite of the isolation the design is built on, so it needs its own decision), thumbnails (Pillow, needs the owner's yes), and a check of the bucket in `/readyz` (a network call per probe; the 503 above says it when it is down).

**Slice 8 (2026-10-06): a security read of the server, and request bodies that refuse unknown fields.** A self-review by reading the code of the places the generated tests reach least: the sign-in routes, the file and export routes, and every place a query is built from pieces. It is **not** the independent review or the penetration test the launch checklist still asks for.

- **Found and fixed.** Six JSON request bodies ignored fields they did not know (the plan-code redeem, the delete-account confirmation and the four operator forms: invite, plan override, grant code, and the reason for a revoke), while every other body already refused them. An ignored field is not an injection, but a mistyped *optional* field is a silent wrong answer: an operator who mistyped `expires_at` on a plan override would have given a plan with no end. All six now answer 422, and a new test (`test_every_json_request_body_refuses_fields_it_does_not_know`) reads the generated API description and **fails for any present or future JSON body that does not**, so the next route cannot forget. The test was seen to fail with one model left open.
- **Read and found sound.** Every query that is built from pieces (eight sites) interpolates only fixed fragments (a literal table name, a fixed list of columns, or a `WHERE` assembled from constant text) and binds every value as a parameter, including the operator's search box. The after-sign-in address (`next`) is checked against a rule that refuses another site, `//`, a backslash, a control character and the sign-in routes themselves, and tests carry each. The callback's redirect target is always one of a fixed set of codes. The sign-in state cookie is used up whatever happens. A person's picture is served with a content type the server detected from the file's header, never the browser's, and a name it made itself. The download-your-data route builds the ZIP in a spooled temporary file, at most two at once per process, with a per-person limit and an audit row; no file name inside the ZIP is made from anything a person typed (they are table names, ids and dates). There is no outbound request whose address a person can influence (the only ones go to the identity provider named in the settings and to the bucket).
- **Noted, not changed.** An export reads each picture from the bucket one at a time, inside the one database snapshot that makes it consistent. That is fine at the beta's size and is the reason to move the export to a background job if journals with thousands of pictures appear. A bucket that is down during an export fails the whole download with a 503 rather than listing every picture as missing, which is the right choice (the manifest's "missing" list should mean missing).
- **Not done.** Nothing here replaces a review by someone else, a scan of the running system (ZAP), or a penetration test; those are on the launch checklist.

**Slice 9 (2026-10-09): the path to a first deploy** (`pg/provision_hosted.py`, `render.yaml`, `docs/runbooks/first-deploy.md`). One command now takes a fresh managed Postgres to a database the server can start on: it creates the six roles with random passwords, hands the database and the `public` schema to `tj_owner`, optionally runs the migrations, and writes the settings the web service needs (the two database addresses and the session secret) to a file git ignores. `render.yaml` is a Blueprint for the web service only; the database is made by hand first, because the roles must exist before the service starts.

- **Tested against a stand-in for the host's administrator**, not a superuser: a scratch role with only CREATEROLE and CREATEDB that owns a scratch database. The test then runs the migrations as `tj_owner`, shows the request role cannot create a table, and starts the server in production mode from the written file and gets `/readyz` 200. Mutation checking left no survivor in the new module.
- **What that found, that a superuser-only test would have hidden.** (1) Since Postgres 16 a role without SUPERUSER or BYPASSRLS may not even *mention* them in `ALTER ROLE` (not to turn them off either), so re-applying all attributes to a role that exists, which the development script does, fails for a host's administrator; the hosted path only sets the password on an existing role and `verify` reports a role whose attributes are wrong. (2) Changing the owner of the `public` schema needs CREATE on the database, which the old owner of the database has and a role that has just handed the database over does not; the schema is now handed over first.
- **Not done.** Nothing has run on Render yet. The plan names in `render.yaml` and the prices in the runbook come from Render's documentation and third-party summaries and are marked *check*. Migrations on a later release are still a manual step (the owner's address stays off the web service on purpose).

**Slice 10 (2026-10-09): a second copy of the screenshot bucket** (`filebackup.py`, `tests/test_filebackup.py`). R2 has no versioning (slice 9's finding), so recovery from a bad deletion, a bug or a leaked token needs another copy. `python -m tradejournal.filebackup [--apply]` copies the keys the second bucket lacks (pictures never change, so "which keys are missing" is the whole algorithm) and forgets, after a keep time (30 days), what has been gone from the source that long, tracked in a small `state/missing.json` in the copy so the clock runs between runs. The privacy cost is explicit: a deleted account's pictures stay in the copy for up to that long. Guards: it forgets nothing when the source lists nothing while the copy holds files (a wrong bucket looks like that), at most 200 keys a run, and it refuses when source and copy are the same bucket. 26 tests including two real bucket servers over signed HTTP; mutation checked (19 mutants, none survive). **Built and not in use**: it needs a second bucket (preferably at another provider), a token, `TJ_BACKUP_S3_*` and a daily job, all the owner's accounts, and a restore done once.

**Slice 4 (2026-10-05): demo mode** (requirement F-P2; `frontend/src/lib/demoMode.ts`, `components/DataSourceRoot.tsx`, `lib/data/defaultSource*.ts`, `scripts/check-bundle.mjs`). **Slice 5 (2026-10-09): the beta's data model and rules** (requirement F-O5; migration `0014_beta_signups.sql`, `pg/beta.py`, `pg/plans.py`, `entitlements.py`, `auth/flow.py`, `docs/runbooks/beta.md`). The first backend step of the front-door rework: who may sign up, with what, and what ending means. No page and no email yet.

- **A personal code per person.** `beta_signups` (address, first name, favourite prop firm) and `beta_join`, a security-definer function the sign-in role may call (and nothing underneath it): it makes an ordinary invite tied to the address, single use, 14 days, carrying a **30-day Pro grant**. The rules are in SQL: one code an hour per address, five in all, none for an existing account or a used code, none while the beta grant is revoked; a new code withdraws the old; one request at a time per address; an audit row that names the sign-up and never the address.
- **Thirty days at most** for any code that gives full access (`plans.MAX_GRANT_DAYS`, a database CHECK for new rows, the operator form and its API limit).
- **Ending.** A grant can be ended early (`grant_redemptions.revoked_at`) and carries when its "ended" email was sent. `entitlements.access_of` and `plans.access` say **ended** only for someone on the free plan because time-limited access ran out or was ended; nobody else is touched, so the rule can be switched on for an account that never had an end date without changing it.
- **Closing a hole.** A sign-up whose invite carries a grant that can no longer be given used to go ahead without it, leaving an account with no end date. It is now undone and the code is not used up.
- **Before Kinde.** `/auth/login?invite=` checks the code first and sends a wrong, used, expired or withdrawn one straight back to the page with the one error code, so no identity is made at the provider for it; a code tied to an address pre-fills it (`login_hint`). The callback still decides.

The race test found that the first version let two simultaneous requests make two codes; a code now counts as on its way until its email is reported failed.
